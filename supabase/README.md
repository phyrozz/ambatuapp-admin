# Dev Firestore → Postgres schema rehearsal

The data source is the 71-document `ambatuapp-dev` export already loaded into `migration_staging.firestore_documents` in the Supabase **ambatu-db-dev** project. Keep that raw table and the private CSV. These scripts do not connect to Firestore, change deployed APIs, create Auth accounts, or touch AWS media/chat.

## Run in your existing Supabase psql connection

First confirm in the dashboard that the connection parameters are for **ambatu-db-dev**. Run each line separately at the `postgres=>` prompt:

```text
\set ON_ERROR_STOP on
\i 'C:/Users/joshu/github/ambatuapp/admin/supabase/migrations/001_app_schema.sql'
\i 'C:/Users/joshu/github/ambatuapp/admin/supabase/migrations/002_import_firestore_dev.sql'
\i 'C:/Users/joshu/github/ambatuapp/admin/supabase/verify_firestore_dev.sql'
```

`001` creates the `app` schema once and fails if it already exists. `002` is transactional: it either imports the entire supported dataset or rolls back. A completed import records all **71 source paths**. Two reciprocal follow documents share one follow row, so destination counts need not add up to 71. Running `002` again with identical staging data makes no row changes; changed staging or a populated destination without a matching marker is rejected. On an SQL error, run `ROLLBACK;` before any next command and inspect the error. Never ignore a failed script or reset the schema with a cascading drop on a database containing application work.

The script validates the staging document project/database as `ambatuapp-dev/(default)`, but cannot tell which Supabase project it is connected to. Target selection must be verified independently. Do not use this as a production cutover script.

## Schema decisions

| Area | Destination | Reason |
| --- | --- | --- |
| Players | `player_profiles`, `username_claims`, `profile_avatars`, `avatar_moderation` | Keep profile IDs, exact normalized username claims, optional profiles, and moderation history. |
| Follows | `follows` | One directed edge replaces the matching following/follower pair. Disagreement aborts rather than guessing. |
| Friends | `friendships` | One row per viewer retains each person's pin, incoming/outgoing direction, and accepted state. Reciprocal state must agree. |
| Content | `content` plus `characters`, `lores`, `videos`, `sounds` | Shared status, ownership, timestamps, and counters with separate content-specific fields. Composite kind/ID avoids collisions across Firestore collections. |
| Interactions | `comments`, `content_votes`, `comment_votes`, `content_visitors` | Foreign keys preserve content and reply context; voter keys preserve the legacy `user:` prefix. Hashed view/listen identities remain hashes. |
| Games | `leaderboard_entries` | Composite game/player identity and ranking index; no requirement for a Firestore game parent document. |
| Studio | `studio_users`, `studio_roles`, `studio_role_permissions`, `studio_modules`, `studio_role_types`, `studio_settings` | Permission rows reference modules/actions; roles are separate from Cognito identity. Imported role assignment counters are snapshots to reconcile. |
| Limits | `public_api_rate_limits` | Preserve current window state as JSONB during the rehearsal; future APIs must enforce updates atomically. |
| Audit | `migration_runs`, `migration_documents` | Dataset fingerprint and a source-to-destination mapping for every staged document. |

All original IDs are text. Player and Studio Cognito pools are distinct, and valid users may not have saved a profile; owner/author/voter IDs therefore do not have profile or Supabase `auth.users` foreign keys. S3 keys remain keys, with signed URLs generated by the API later.

Typed source JSON remains in staging. Supported scalar fields become SQL columns; unused fields remain in `extra` JSONB (or the original staging document for mirrored follows). Arrays such as tags, lore image keys, and translation entries remain JSONB arrays. Legacy null dates and missing statuses are preserved. In particular, a sound with no status remains public under the current API semantics; future SQL queries must explicitly include that case.

SQL timestamps have microsecond precision. Nanosecond timestamp strings remain available in the source JSON, but SQL timestamps may round. Future cursors must use the new SQL timestamp plus a stable ID and must not reuse Firestore timestamp cursors. Indexes support chronological, popularity, creator, comment, friend, and leaderboard keyset pagination. No numbered pagination is introduced.

## Access

After migrations 001 and 002, `app` is a private schema with RLS enabled on every table, no policies, and no privileges for `PUBLIC`, `anon`, `authenticated`, or `service_role`. Keep both `app` and `migration_staging` out of Supabase's exposed schemas. The current Cognito login does not automatically grant SQL access; do not add `auth.uid()` policies assuming IDs are interchangeable. [The local dev snapshot reader](dev-content-reader.md) adds a dedicated restricted role and policies in migrations 003 and 004. Privileged `postgres` owns the tables and can run these migrations.

Supabase documents [custom schema exposure](https://supabase.com/docs/guides/api/using-custom-schemas) and [how grants and RLS interact](https://supabase.com/docs/guides/database/postgres/row-level-security).

## Validation and next phase

Locally rehearsed on PostgreSQL 18 using the actual dev CSV; this does not assert that your Supabase project has run these scripts. The verification script checks complete path coverage, an exact destination for each path, content detail rows, RLS and privileges, and reports historical username/counter inconsistencies without changing them.

The integration test `tests/schema.test.mjs` uses a disposable database on a local PostgreSQL server. Set `PGTEST_PORT` to that server's port, then run `node --test supabase/tests/schema.test.mjs` from `admin`. The host is fixed to loopback and each run creates/drops a uniquely named test database; it cannot target a Supabase hostname. It covers nested translation/tag conversion, 64-bit integers, null timestamps, legacy sound status, ID collisions across content kinds, replies, listeners, repeated imports, changed datasets, wrong source projects, and rollback on a missing parent. The test skips when `PGTEST_PORT` is unset.

This first schema is deliberately strict about missing relational parents, unknown collection paths, and inconsistent social mirrors. New datasets may expose issues that the dev fixture does not contain; an error rolls back for review. Original counters are preserved, not silently recalculated. Before production, profile missing fields/invalid types, review diagnostics, audit future server privileges, test concurrent votes/friendships/username claims/last-Root safeguards, and rehearse fresh export/cutover/rollback. Current APIs still use Firestore.
